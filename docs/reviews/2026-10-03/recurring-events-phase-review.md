# Phase 56 — recurring event windows

## Purpose and implemented behavior

A one-time announcement must not satisfy an ongoing quarterly expectation forever. Event conditions now offer one window, or 2–12 monthly, quarterly or yearly windows, with a preview of every inclusive UTC date range before approval. The complete schedule is bounded to 3,650 days and cannot overlap. Existing definitions remain one-time events. This extends the existing private revision, event check, optional watch, assessment, Updates and export workflow.

Month-end anchors stay at month end. Other dates retain their original day where possible and clamp in shorter months without drifting: January 30 → February 28 → March 30. July 1–September 30 every three months becomes October 1–December 31. A gap retains the preceding window's deadline state; after the final window, no additional periods are invented. Changing recurrence resets approval and creates a new immutable revision; pending event edits preserve the selected recurrence and date meaning.

Each check records its concrete window, and reuse requires that exact window plus the existing revision/source contract. At a new window, an earlier result cannot supply a finding, quotation or review identity. The code creates an unknown assessment and reviewable period transition without a source or model request. Optional approved-event watches can evaluate the new window at their next existing acquisition cadence; the clock transition itself does not spend credits. Source coverage is still separate from condition outcome.

The user can explicitly select an earlier window for late evidence in the current saved source snapshot. Such a check stays in History and cannot replace current monitoring. Future numbered windows and foreign/nonrecurring conditions are rejected before a model call. If any chosen condition is historical, the complete multi-condition check is historical-only; use the current-window selection to assess current monitoring. A check finishing after rollover is also history-only. Immutable earlier responses remain accessible. The window selector does not retrieve an older article archive.

Date meaning remains explicit. **Report published during** requires a qualifying report in each window; a newer report about an older event may meet that definition. Choose **Event happened during** when the completed event itself must occur in each period. Occurrence still requires a full source-stated date and retains all phase55 timing/interpretation limits. The model prompts and pricing profiles are unchanged; recurrence arithmetic and result binding belong to code.

## Five-perspective review

These are five perspectives applied by one coding agent, not independent consultants or participant research.

| Perspective | Judgment and consequence |
| --- | --- |
| Product | Recurring expectations now require fresh period-specific evidence and create a reviewable reset. This makes an ongoing thesis monitor more faithful than an indefinitely satisfied event checkbox. Expected filing calendars remain a separate missing capability. |
| Research quality | Code binds each result to exact dates and preserves original quotations. Actual-source replay demonstrates isolation across periods, not whether the model consistently recognizes real events or whether source sampling captures all relevant evidence. |
| UX | Users see the full schedule before approval and the exact checked window in results/history/export. Monthly/quarterly labels alone would conceal month-end behavior, so the preview is essential. Historical checks are explicit and cannot silently affect current state. Beginner comprehension remains unmeasured. |
| Architecture | Two additive fields and the existing immutable packet/queue pipeline suffice. No new provider, model stage or scheduler is introduced. Clock catch-up, cached inputs, response completion and current-window selection are independently guarded. |
| Business | A recurring evidence expectation supplies a concrete reason to revisit a saved idea. Zero incremental development API spending says nothing about production cost, natural retention, alert usefulness or willingness to pay. |

Install this bounded recurrence capability.
