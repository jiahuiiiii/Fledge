# Independent technical architecture and data-engineering review

Thesis is feasible as a narrow research-and-monitoring application. The proposed single API, worker and PostgreSQL deployment is suitable for a small team. The whole feature catalogue is too large for its first integrated release: company research, expectations, scenarios, chat, proposals, several notification channels and historical evaluation create multiple products' worth of integration work. Keep the architecture, but commit first to one recorded company, a small metric set, one approved idea and an in-app evidence-change review. Twenty-four tables are not themselves the problem; unimplemented behavioural contracts are.

This review inspected the planning files and complete SQL draft. It did not inspect the live application repositories or rerun database tests. The earlier selected PostgreSQL checks are documented evidence, not proof of application integration ([README, line 29](../../../README.md)). Reuse is authorized; code ownership is not an integration blocker.

Two strengths deserve preservation:

- **The historical model asks the right question.** Stable condition identities, separate definitions and exact thesis-version membership prevent the easy mistake of displaying today's threshold beside yesterday's result. Composite foreign keys connect results to the evaluated revision ([schema, lines 135–153](../../archive/planning/schema.sql), [190–244](../../archive/planning/schema.sql)).
- **The integration boundaries are practical.** One codebase, separate research/monitoring namespaces, one scheduler, shared company research and private evaluation avoid recreating both applications wholesale. Optional libraries remain optional ([database design, line 18](../../archive/planning/database-design.md), [architecture, lines 127–129](../../archive/planning/architecture.md)).

The following issues are ranked by importance for the first working release.

1. **Make revision integrity executable before connecting the editor.** This is a correctness requirement. The document specifies locking, expected revisions, complete results and atomic approvals, but those are still service rules ([database design, lines 83–95](../../archive/planning/database-design.md)). SQL permits an evaluation marked `met` without condition-result rows; owner-only policies do not make old versions immutable. Proposal foreign keys establish owner/thesis relationships, but do not establish that the target condition belonged to the proposal's base revision or that its instrument matches. The consequence is plausible-looking history with incomplete or incorrectly applied decisions. Implement one transaction service for revision saves and approvals, with typed payload validation and optimistic revision checks; publish evaluations only with complete results. Restrict ordinary writers from updating historical semantic records. Select displayed status by the current revision. Do not keep the existing multipart editor mutations as a normal write path: the design already acknowledges partial-save risk ([line 81](../../archive/planning/database-design.md)).

2. **Define the numerical and temporal contract more tightly.** This is a correctness requirement before automated condition evaluation. Observations have periods and currency, but quantitative conditions contain a metric, operator, threshold and untyped `scope`; the accepted period, currency, adjustment convention and reported-versus-expected meaning are not specified there ([schema, lines 79–98](../../archive/planning/schema.sql), [164–188](../../archive/planning/schema.sql)). A quarterly growth fact can therefore be structurally valid while answering an annual question. Evaluation records hold an input fingerprint, but no explicit complete input manifest; citations record selected evidence, not necessarily everything assessed ([205–260](../../archive/planning/schema.sql)). Start with a small typed metric/condition contract and reject incompatible inputs. Persist the exact input IDs, evaluation mode and effective time; define whether cutoff and deadline expiry enter the fingerprint. Constrain supersession to the same document or fact identity: current `supersedes_id` foreign keys only require another row to exist ([lines 61 and 96](../../archive/planning/schema.sql)).

3. **Finish the authorization boundary before introducing multiple accounts or restricted sources.** The private-row RLS and owner-qualified foreign keys are useful. However, the schema intentionally supplies no production grants; shared evidence uses textual entitlement labels and API enforcement ([schema, lines 102–110](../../archive/planning/schema.sql), [364–388](../../archive/planning/schema.sql)). A tenant policy does not protect a cached shared brief containing evidence the requester cannot access. Implement a server-derived transaction account context, restricted API/worker roles and one entitlement-aware evidence access layer used by direct retrieval, briefs, exports, chat and caches. For the first slice, one permitted source scope is enough; a general entitlement platform can wait. PostgreSQL confirms that superusers and `BYPASSRLS` roles bypass these policies, so the actual application role must be tested ([official RLS documentation](https://www.postgresql.org/docs/current/ddl-rowsecurity.html)). This is a deployment gap, not evidence that an inspected live app leaks data.

4. **Persist coverage and recovery state, not only successful outputs.** This is essential for truthful monitoring. The plan promises cursors, outage recovery and a distinction between no new evidence and supplier failure ([architecture, lines 115–120](../../archive/planning/architecture.md)). The SQL's source record has no durable check interval, cursor or gap history. Queue history alone is not a domain-level coverage contract. Add a minimal source-check/checkpoint record with successful coverage, cursor, errors and gaps. Advance it only when ingestion commits. The call and delivery tables provide useful identity/status foundations ([schema, lines 325–355](../../archive/planning/schema.sql)); define recovery for abandoned `running`/`sending` states, unknown charges and concurrent cost reservations. Keep external sends and model calls out of retryable database transactions. Start with in-app alerts and a fake model gateway, proving restart behaviour before external delivery or spending.

5. **Turn the broad API migration into one bounded cutover.** This is the main team-capacity issue. The plan correctly treats current frontend code as authoritative and preserves `/api/v1`, IDs and response envelopes ([database design, lines 65–81](../../archive/planning/database-design.md)). Yet draft saving, explicit review actions and notification preferences are promised without a completed persistence contract ([UX, lines 40 and 95](../../archive/planning/ux-and-user-journey.md), [database design, lines 101–109](../../archive/planning/database-design.md)). Freeze representative request/response fixtures and implement only the chosen journey, including its draft/approval distinction and review record. Delay scenarios, social ingestion, embeddings, paid tiers and historical strategy research. Import existing data only after an inventory; preserve missing history as unknown instead of synthesizing it.

Implement the vertical slice in this order:

1. Freeze frontend contracts, fictional fixtures and the supported condition vocabulary; choose one migration authority.
2. Create the fresh development database, restricted roles and transaction services; connect atomic saving and version-correct history.
3. Feed recorded documents/facts into one brief, one approved idea and deterministic evaluation, including adverse and missing evidence.
4. Add durable acquisition coverage, the worker and transactional in-app alerts; demonstrate recovery and explicit user review.
5. Only then substitute permitted live adapters and an approved model gateway, measure operating cost and consider legacy-data cutover.

Acceptance should include concurrent edits and duplicate approvals; an old job finishing after an edit; denial of historical updates; omitted condition results; different units/periods; restatements after the cutoff; expiry without new evidence; two accounts using the same pooled connection; denied-source retrieval through every response path; outages versus successful empty polls; and worker crashes before/after commits. Also test ambiguous provider outcomes with mocks, then backup/restore the resulting history. These checks establish functional boundaries; they do not establish investment usefulness.

Remaining uncertainties are the actual adapter/authentication quality, existing-data volume, selected provider entitlements, team availability and the evaluator's business semantics. Those prevent a credible delivery estimate now. An integration spike can resolve them without widening the product or adding infrastructure.
